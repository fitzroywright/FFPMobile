# Architecture

The mobile clients are three native Android apps under `android/`. Each has its own application sandbox, Keystore and release lifecycle. The shared Compose shell renders sign-in and a preview that has no access to account sessions or transaction repositories. Each feature module defines the screens for its own app.

`core-network` uses Retrofit and OkHttp over HTTPS. `core-auth` contains an initial login client behind a closed commissioning gate. The current Warehouse API requires tablet enrollment and signed requests, which the Kotlin clients still need to integrate. `core-security` wraps sensitive storage with Android Keystore and validates the signature, scope and expiry of a cached authorization document. Enrollment still must provision the verifier and a trustworthy time source. Effective FFP Manager XAF permissions remain authoritative. See [Common.Security integration](COMMON-SECURITY-LOGIN.md).

The Warehouse app includes `core-database` and `core-sync`. The Room outbox is encrypted by SQLCipher using a randomly generated passphrase wrapped with an Android Keystore AES-GCM key. Each submission uses a stable UUID as its idempotency key. WorkManager uses network constraints, exponential retry for transient I/O failures and periodic recovery. Rows are scoped to the app and account. A matching server receipt with a newer revision advances the row. Locally saved, received, accepted, approved, posted, conflicted and rejected stages are individually represented. A conflict preserves the issue for reconciliation. The repository and worker remain dormant pending a live session provider and server transaction protocol.

The private API under `services/FFPMobile.Api` owns server-side identity and authorization through Common.Security and the permission resolver interface. Send device traffic through that API on the private network or VPN. FFP Manager SQL Server and the Request Portal Bridge stay outside the Android integration. Keep ERP-specific work behind service adapters so a Business Central adapter can replace the FFP Manager implementation. Security Post workflows require their own authorization scope. A dispatch cache cannot authorize a physical release.
